# Nyx 生成式交互探索草稿

> Status: living brainstorm
>
> 这是一张可以持续涂改的探索地图，不是排期、PRD 或 scope 授权。把想法写进来，不代表 Nyx 现在就要实现它。真正开始实验时，需要单独挑出一个边界清楚的小切片，并显式确认它进入当前工作范围。

Nyx 首先是我给自己使用的 AI 客户端，也是一个长期探索人和 AI 如何一起工作的实验场。

这里不追逐“为了领先而领先”。我会从自己的真实使用出发，反复尝试那些让我好奇的交互：输入框还能是什么，回答能否被直接操作，界面能不能理解当前意图，又该在什么时候保持安静。领先如果发生，应该是长期追问这些问题留下的副产品。

当前产品范围仍以 [v1 min chat](../v1-min-chat-implementation-plan.md) 为准。已经建立的 thread、provider、durability 和安全边界要继续稳定；这份文档只保存未来可能探索的方向。

## 怎么使用这份草稿

- 平时遇到新想法，先原样记下来，不急着补成完整方案。
- 时间充足时，只挑一个最想亲手体验的问题。
- 每次实验都做成一个能真正使用的小循环，而不是一堆彼此等待的基础设施。
- 实验结束后，可以保留、删除或分叉。删除不是失败，它说明这个方向已经被真实触摸过。
- 不用 KPI 给概念实验制造虚假的确定性。回到使用感受，记录它哪里真的改变了行为。

每次只问几个问题：

1. 哪个瞬间真的让我觉得“原来还可以这样”？
2. 哪些部分只是看起来酷，用一次就够了？
3. 我有没有在之后自然地再次使用它？
4. 它是否沉淀出一种可以复用的 Nyx 交互语言？
5. 这次实验又打开了什么新问题？

## 稳定内核与实验边缘

Nyx 可以大胆，但不能每次实验都把整个产品一起变成实验品。

稳定内核负责让人放心：对话、流式响应、停止、重试、当前 thread 的持久化、provider 与凭据边界、失败恢复和显式重新开始。它们不需要抢镜，只需要可靠。

实验边缘负责提出新问题：Composer、消息内容、富结果、Artifact、选择与直接操作、界面形态、动效和空间关系。实验尽量长在这些表面上；只有表面证明了新的状态能力确实有价值，才考虑改变更深的运行时边界。

## 先遵守的几条交互判断

- 惊叹应该来自行为。贴上一张图，系统立刻理解上下文，比一个发光的上传按钮更有意义。
- 空间关系要稳定，内容表达可以大胆。用户不该每轮都重新学习按钮在哪里。
- 语言和直接操作应当修改同一份状态。用户拖动、选择或改写之后，AI 要知道发生了什么。
- 生成出来的东西仍然要可检查、可撤销、可继续编辑。神奇不能以失控为代价。
- 能力按需要出现。普通聊天仍然像普通聊天；只有任务需要时，界面才逐步展开。
- 数据不丢、凭据不泄露、键盘可达和清晰反馈不是概念实验可以省略的部分。

## 探索地图

下面大致从今天的文本聊天向更自由的生成式界面延伸。它表达的是能力之间可能的关系，不是必须按顺序完成的路线。

| 探索方向              | 想追问的问题                                               | 可以先玩的概念                                                       |
| --------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------- |
| 多模态上下文 Composer | 输入框能否从“写一句话”变成“组织这次对话所需的上下文”？     | 粘贴截图、拖入图片、附件预览、无文字发送、失败后不丢内容             |
| 富内容响应            | 回答除了连续文字，还能用什么结构自然生长？                 | 流式出现的代码、表格、引用、步骤和可折叠证据，而不是等整块内容完成   |
| Artifact Stage        | 一个结果什么时候应该离开消息气泡，成为可以持续工作的对象？ | 让文档、图表、代码或网页在稳定的侧边舞台中打开，并保留与对话的联系   |
| 选择即上下文          | “这个”“这里”“刚才那一段”能否成为精确输入？                 | 选择消息片段、图片区域或 Artifact 节点后，直接带入 Composer 继续追问 |
| 可塑 Artifact         | 提示词和直接操作能否共同编辑同一个结果？                   | 一边拖动、改字、调整数据，一边让 AI 理解这些改动并继续生成           |
| 会变形的任务界面      | 界面能否随意图变化，同时保留位置、状态和控制感？           | 一段回答逐步长成表单、时间线、比较器或调试面板，而不是突然替换整屏   |
| 受控生成式 UI         | 模型能否组合 Nyx 信任的原生组件，生成可靠又有个性的交互？  | 使用有限组件词汇表达动态布局、动作和状态，宿主掌握执行权             |
| 隔离运行的小应用      | 什么时候值得允许更自由的 HTML、样式和脚本？                | 把真正需要自由表达的结果放进隔离沙箱，与宿主通过窄协议通信           |

这里可能长期存在两条并行路线：一条使用 Nyx 自己的可信组件，追求原生、连贯和可控；另一条运行隔离的小应用，追求更自由的表达。没有必要过早把它们统一成一种宏大协议。

## 一次实验的最小记录

每次准备动手前，只需要补齐下面这些内容：

```text
实验名：
这次只追问什么：
希望出现的惊叹瞬间：
最小可用循环：
明确不做什么：
会新增哪些用户可见状态：
哪些稳定能力不能被破坏：
实验后的真实感受：
决定：保留 / 删除 / 分叉 / 暂停

```

它刻意不是完整 PRD。等一个实验真的要进入实现，再把必要的产品、设计和技术决策写进独立切片。

## Experiment 01：上下文 Composer

**状态：** 正在形成方案。

**这次只追问：** 当文本框能够自然接住图片时，Composer 会不会开始像一个“上下文容器”，同时仍然保留文本输入的速度和熟悉感？

**希望出现的瞬间：** 正在描述问题时直接按下粘贴，截图安静地进入 Composer；没有模式切换，没有上传流程打断思路。发送后，图片和文字仍是这次对话里清晰、可恢复的一部分。

**最小可用循环：**

1. 通过粘贴、拖放或文件选择加入图片。
2. 在发送前预览、查看基本状态并移除图片。
3. 图片可以和文字一起发送，也可以单独发送。
4. 用户消息准确展示本次发送的图片与文字。
5. 模型收到真实的多模态内容，assistant 继续沿用当前可靠的文字流式响应。
6. 失败、重试和应用重启不会让已发送的图片失去含义。

**第一轮明确不做：** 通用文件管理器、文档解析、音视频、图片编辑与标注、云端资源库、富文本编辑器、Artifact 舞台、assistant 生成图片，以及自由 HTML 渲染。

这个边界不是因为后面的方向不重要。先让“粘贴一张图并继续说话”成为一个完整、顺滑、可信的动作，才能知道下一步应该探索引用、圈选，还是更多类型的上下文。

## 灵感收件箱

这些只是种子，可以随时改写或删除：

- 粘贴截图后，直接圈出区域再提问。
- 把回答中的一段拖进 Composer，让它变成下一轮可见的上下文。
- 流式响应不是逐字打印，而是结构逐渐长出来。
- 一句“把它变成可以比较的版本”，让文字原位变成可操作的比较器。
- Artifact 中的手动修改自动成为下一轮上下文，不需要重新描述。
- 为一次任务临时生成控制面板，任务结束后自然收起。
- 在同一结果上保留几个分叉，能看见每次变形从哪里开始。
- 让生成式界面解释自己：它用了什么数据、会执行什么动作、如何回到之前。
